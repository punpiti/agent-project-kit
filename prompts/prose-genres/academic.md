ใช้ร่วมกับ `prompts/24_PROSE_STYLE.md` เสมอ ไฟล์นี้เพิ่มเฉพาะชั้นตรวจของงานวิชาการ
Checker profile: `python3 scripts/check_prose_style.py FILE --profile academic`
(รายงาน `review` candidates ของวลี artifact/meta-writing ด้วย)

## A. Scientific-reporting and trust gate สำหรับงานวิชาการ

ใช้ส่วนนี้กับ paper, thesis, proposal, technical report และข้อความที่รายงานวิธีหรือผล
เป้าหมายไม่ใช่การซ่อนว่าใช้ AI แต่คือทำให้ต้นฉบับ self-contained, ตรวจสอบได้ และไม่ใช้
provenance ของไฟล์หรือโค้ดแทนเหตุผลทางวิทยาศาสตร์

1. **Methods ทุกประโยคต้องมีหน้าที่ทางวิทยาศาสตร์** อย่างน้อยหนึ่งอย่าง: ระบุข้อมูลเข้า,
   การแปลง/การคำนวณ, พารามิเตอร์หรือเกณฑ์, เหตุผลรองรับ, หรือผลผลิตที่นำไปวิเคราะห์ต่อ
2. **ใช้ชื่อวัตถุจริงแทนชื่อ artifact ภายใน** เช่น `reconstructed rainfall fields` หรือ
   `storm-level indicators` แทน `analysis cache`, `stored metrics` หรือชื่อ notebook
   เว้นแต่ artifact นั้นเป็นส่วนของ reproducibility contract ที่ผู้อ่านต้องเข้าถึงจริง
3. **อย่าใช้ provenance เป็น justification** การพบค่า threshold ใน workflow, archive,
   notebook หรือโค้ดเดิมบอกเพียงที่มา ถ้ายังไม่มี calibration หรือหลักฐานทางวิทยาศาสตร์
   ให้เรียกค่าตามหน้าที่จริง เช่น `historical input-error screen` และบอกข้อจำกัดครั้งเดียว
4. **ต้นฉบับต้องอธิบายวิธีที่จำเป็นได้เอง** ห้ามฝากสาระไว้กับ notebook, repository,
   caption หรือ supplement โดยไม่บอกขั้นตอนและพารามิเตอร์ขั้นต่ำใน Methods
5. **caption อธิบายรูป; Methods อธิบายวิธี** ตัดประโยคชี้ทาง เช่น “its caption
   summarizes the sequence” แล้ววางสาระไว้ในส่วนที่ผู้อ่านคาดว่าจะพบ
6. **แยก reproducibility ออกจาก validity** การรันซ้ำได้, มี cache ครบ หรือมี lineage
   ไม่ได้พิสูจน์ว่า reconstruction, anchoring, optical flow, threshold หรือการตีความเหมาะสม
7. **ตรวจ lineage ก่อนเกลาภาษา** ถ้าวิธีหรือพารามิเตอร์เปลี่ยน ให้เชื่อม input → setting →
   derived field/metric → figure/table/claim และคำนวณผลกระทบปลายน้ำใหม่ก่อน rewrite
8. **ใช้คำเรียกคงที่ตาม data model** ทำ terminology map สำหรับข้อมูลดิบ, ข้อมูลหลัง QC,
   reconstructed fields, analysis windows, indicators, classes และ validation evidence
9. **แยก operational definition จาก independent validation** การจัดกลุ่มด้วยกฎภายใน
   บอกผลของกฎนั้น ส่วนความถูกต้องทางกายภาพหรือ meteorological skill ต้องใช้หลักฐานอิสระ
10. **แยก AI disclosure จาก Methods** disclosure ระบุชื่อเครื่องมือ วัตถุประสงค์ ขอบเขต
    และความรับผิดชอบของผู้เขียน ส่วน Methods ต้องยืนได้ด้วยข้อมูล เหตุผล และหลักฐานของวิธีเอง

ก่อนผ่าน gate ให้ตอบคำถามต่อไปนี้จากข้อความในต้นฉบับได้โดยไม่เปิดไฟล์ทำงานภายใน:

| คำถาม | หลักฐานที่ควรอยู่ในต้นฉบับ |
|---|---|
| ใช้ข้อมูลอะไร | ชนิด แหล่ง ช่วงเวลา หน่วย ขอบเขต และข้อจำกัดที่มีผลต่อการตีความ |
| ทำอะไรกับข้อมูล | ลำดับการประมวลผลที่เปลี่ยนข้อมูลหรือสร้างตัวชี้วัด |
| ใช้ค่าใดและเพราะอะไร | ค่า พิสัย/หน่วย บทบาท และฐานสนับสนุนหรือสถานะว่าไม่ได้ calibrate |
| ได้ผลผลิตอะไร | ชื่อวัตถุจริงที่เชื่อมต่อกับผล รูป ตาราง หรือ claim |
| วิธีเปลี่ยนแล้วผลใดต้องคำนวณใหม่ | lineage และ impact/sensitivity check ของผลปลายน้ำ |
| อะไรเป็นเพียง operational grouping | ขอบเขต claim และ independent evidence ที่ยังขาด |

บทเรียนด้านหลักฐาน: editor อาจตั้งข้อกังวลเรื่อง methodology และการใช้ AI ขณะที่ public
review วิจารณ์ภาษาและวิธีโดยไม่ระบุว่าประโยคใดสร้างด้วย AI ได้ ห้ามรวมหลักฐานสองชุดนี้
เป็นคำกล่าวว่า reviewer “ตรวจพบ AI จากสำนวน” ถ้าไม่มีข้อความนั้นโดยตรง รูปแบบภาษาและ
คำศัพท์ภายในเป็นสัญญาณให้ตรวจความชัดเจนและความน่าเชื่อถือ ไม่ใช่เครื่องพิสูจน์ผู้เขียนหรือเครื่องมือ

## ชื่อที่สื่อความหมายและภาระความจำของผู้อ่าน

- **ห้ามอ้างรหัส config ของชุดการทดลองในบทความ** ตั้งชื่อที่อ่านแล้วเข้าใจทันทีว่า
  ชุดทดลองนั้นทำอะไร ใช้ข้อมูลหรือวิธีใด หรือเปลี่ยนเงื่อนไขใด เช่น
  “แบบจำลองที่ใช้เฉพาะข้อมูลเรดาร์” และ “แบบจำลองที่เพิ่มข้อมูลสถานีฝน”
  ห้ามใช้ `C1`, `CFG-A`, `E03` หรือชื่อย่อที่ต้องจำตารางเทียบ แม้เคยนิยามไว้แล้ว
- **ห้ามอ้างคำถามวิจัยด้วยรหัส เช่น `RQ1`, `RQ2`** ให้กล่าวถึงสาระของคำถามโดยตรง
  เช่น “การเพิ่มข้อมูลสถานีฝนช่วยลดความคลาดเคลื่อนเพียงใด” และเชื่อมผลกับคำถามนั้น
  ด้วยข้อความที่มีความหมายในตัวเอง ไม่เขียน “ผลนี้ตอบ RQ2”
- ใช้ชื่อเชิงความหมายที่คงที่และแยกความต่างของชุดทดลองได้จริงตลอดบทความ รวมถึง
  หัวข้อ ตาราง ป้ายกำกับในรูป คำบรรยายรูป/ตาราง และเอกสารเสริมที่ผู้อ่านใช้
  ถ้าค่าพารามิเตอร์เป็นสาระที่เปรียบเทียบ ให้ระบุค่าและหน่วยตรง ๆ ในชื่อหรือข้อความ
- รหัสสำหรับรันงานและการจับคู่กับชื่อที่เผยแพร่เก็บได้ใน config, โค้ด หรือบันทึกภายใน
  แต่ไม่ยกมาอ้างในบทความ การมีคำอธิบายรหัสไว้ครั้งแรกไม่ทำให้ผ่านกฎนี้
- เหตุผลคือรหัสเพิ่มภาระ working memory: ผู้อ่านต้องจำและแปลรหัสกลับเป็นสาระ
  ตรวจโดยอ่านแต่ละข้อความหรือป้ายกำกับแยกจากตารางเทียบ แล้วต้องเข้าใจได้ทันที
  ว่ากำลังกล่าวถึงการทดลองหรือคำถามใด

## น้ำเสียงตามข้อเท็จจริงและความเป็นธรรมในการเปรียบเทียบ

- **อย่าให้พฤติกรรมในบทสนทนาขยายความสำคัญของประเด็นเกินจริง** ใช้กับทุกประเด็น
  ทั้งคู่เทียบ วิธี รายละเอียดทางเทคนิค ข้อจำกัด และผลย่อย การคุยนาน คุยซ้ำ ถามเจาะ
  หรือแก้หลายรอบอาจเป็นเพียงการแก้ปัญหาเฉพาะจุด ไม่ใช่หลักฐานว่าประเด็นนั้นสำคัญ
  ต่อบทความ ให้จัดน้ำหนักตามความสัมพันธ์กับคำถามวิจัย ผลกระทบต่อข้อสรุป และหลักฐาน
  ห้ามยกประเด็นรองเป็น contribution หลัก ข้อค้นพบสำคัญ หรือข้อจำกัดหลักเพียงเพราะ
  ใช้เวลาคุยมาก และห้ามเพิ่มน้ำหนักในชื่อเรื่อง บทคัดย่อ บทนำ อภิปราย หรือบทสรุป
  โดยอัตโนมัติ หลังแก้เฉพาะจุดให้ตรวจทั้งฉบับและย่อหรือรวมข้อความที่ได้รับพื้นที่เกินบทบาท
- **ตรวจว่าไม่เขียนดูถูกหรือลดคุณค่างานตัวเอง** ตัดคำตัดสินเชิงคุณค่าที่ไม่มี
  หลักฐาน เช่น “เป็นเพียงการทดลองเล็ก ๆ” หรือ “วิธีของเรายังด้อยมาก” แล้วรายงาน
  ขอบเขต วิธี ผล และข้อจำกัดที่ตรวจสอบได้ เช่น “ประเมินด้วยข้อมูลจากสามสถานี”
  ระบุว่าข้อจำกัดกระทบข้อสรุปใด โดยไม่ขยายให้กลายเป็นคำตัดสินคุณค่าของงานทั้งหมด
- **รายงานตามข้อเท็จจริง** ระบุทั้งผลที่ดี ผลที่ด้อย และความไม่แน่นอนตามหลักฐาน
  ไม่กลบข้อจำกัด ไม่กล่าวอ้างเกินผล และไม่ใช้ความถ่อมตัวแทนคำอธิบายทางวิทยาศาสตร์
- **ไม่ทำให้คู่เทียบตัวใดโดดเด่นเป็นพิเศษด้วยวิธีนำเสนอ** ใช้เกณฑ์ ตัวชี้วัด
  ขอบเขตข้อมูล ระดับรายละเอียด และน้ำเสียงเดียวกันกับทุกวิธี รวมถึงวิธีของผู้เขียน
  ตรวจการเลือกผลมารายงาน ลำดับการเล่า คำขยาย พื้นที่อธิบาย และการเน้นในรูป/ตาราง
  ว่าไม่ชี้นำให้ยกย่องหรือลดคุณค่าวิธีใดโดยไม่มีเหตุผลจากหลักฐาน
- ถ้าผลต่างกันจริง ให้ระบุทิศทาง ขนาดความต่าง เงื่อนไข และความไม่แน่นอนตามที่มี
  ไม่ปรับถ้อยคำให้ดูเสมอกัน และไม่สรุปว่าวิธีหนึ่งเหนือกว่าโดยรวมจากผลเฉพาะเงื่อนไข
- **อย่าใช้ลำดับหรือความถี่ของบทสนทนาอนุมานความสำคัญของคู่เทียบ** การที่ผู้เขียน
  ถามเพิ่ม แก้รายละเอียด หรือกล่าวถึงวิธีหนึ่งในช่วงหลัง ไม่ใช่คำสั่งให้ยกระดับวิธีนั้น
  เป็นประเด็นหลักหรือแยก section เฉพาะ ให้รักษาโครงเรื่องและน้ำหนักตามคำถามวิจัย
  บทบาทของแต่ละวิธี และหลักฐานที่ตกลงไว้ จนกว่าจะมีคำสั่งเปลี่ยนทิศทางอย่างชัดเจน
- **ตรวจความสมมาตรของโครงสร้างหลังคุยแก้หลายรอบ** ก่อนเพิ่ม section ให้คู่เทียบ
  ให้ตรวจว่ามีเหตุผลทางวิทยาศาสตร์ที่ต้องอภิปรายแยกหรือมีคำสั่งชัดเจนจากผู้เขียน
  ถ้าคู่เทียบมีบทบาทระดับเดียวกัน ให้ใช้โครงสร้างร่วมและระดับรายละเอียดที่เทียบกันได้
  หากแยก section ด้วยเหตุผลด้านเนื้อหา ต้องบอกเหตุผลนั้นได้โดยไม่อ้างว่าคุยถึงมาก
  หรือเพิ่งคุยถึง ตรวจทั้งฉบับอีกครั้งว่า section และพื้นที่อธิบายไม่เอนตามบทสนทนาล่าสุด

## ร่างภาษาไทยเพื่อ review (Thai review draft)

ใช้เมื่อต้นฉบับเขียนภาษาอังกฤษ และผู้เขียนกังวลว่ากำแพงภาษาทำให้มองจุดเด่น จุดด้อย
หรือการหลุดประเด็นไม่ชัด ให้แปลและเรียบเรียง manuscript ฉบับล่าสุดเป็นภาษาไทย **ทั้งฉบับ**
เพื่อใช้ review โครงเรื่องและเนื้อหา ร่างไทยเป็นเครื่องมือตรวจ ไม่ใช่ฉบับเผยแพร่
เก็บเป็นไฟล์แยก ระบุฉบับต้นทาง (ชื่อไฟล์/วันที่/commit) และคง section กับลำดับย่อหน้า
ให้เทียบกับต้นฉบับได้ ข้อแก้ที่พบจากร่างไทยต้องนำกลับไปแก้ในต้นฉบับภาษาอังกฤษ

กฎการเขียนร่างไทย (ใช้ร่วมกับกฎทั้งไฟล์นี้และ `24_PROSE_STYLE.md`):

1. **ประโยคเปิดของทุกย่อหน้าต้องคม กระชับ และเป็น punch line ในตัว** ผู้อ่านอ่านแค่
   ประโยคเปิดแล้วรู้ข้อสรุปของย่อหน้า ประโยคที่เหลือทำหน้าที่เสริมด้วยหลักฐาน ตัวเลข
   อ้างอิง หรือเหตุผล ประโยคที่ไม่เสริมประโยคเปิดให้ย้ายหรือตัด
2. **ย่อหน้าแรกเป็นข้อยกเว้น** ย่อหน้าเปิดเกริ่นที่มาเพื่อนำไปสู่ problem statement
   ไม่ต้องเปิดด้วย punch line ย่อหน้าอื่นทั้งหมดต้องสนับสนุนย่อหน้าแรก ถ้าย่อหน้าใด
   ไม่เชื่อมกลับไปที่ problem statement ได้ ให้รายงานว่าเป็นจุดที่อาจหลุดประเด็น
3. **รายงานข้อเท็จจริง ไม่ดูแคลนงานตัวเอง** บอกว่าทำอะไร ด้วยข้อมูลและเงื่อนไขใด
   ห้ามใช้ถ้อยคำลดคุณค่า เช่น “ทำเพียง…”, “ทำแค่…”, “ยังไม่ได้ทำ…”
   ถ้าเห็นว่าขอบเขตหรือปริมาณงานน้อยเกินไป ให้รายงานแยกนอกต้นฉบับ (ในบันทึก review
   ถึงผู้เขียน) ไม่เขียนความเห็นนั้นลงในเนื้อความ
4. **ไม่ใช้คำที่ยังไม่นิยาม** ศัพท์ ตัวย่อ สัญลักษณ์ และชื่อวิธีต้องนิยามก่อนหรือ
   ณ จุดที่ใช้ครั้งแรก ถ้าต้นฉบับอังกฤษใช้คำก่อนนิยาม ให้รายงานเป็นจุดต้องแก้ในต้นฉบับด้วย
5. **ทุกการอ้างอิงต้องเข้าถึงต้นฉบับได้** มี PDF ในโปรเจกต์หรือลิงก์ (DOI/URL)
   ที่เปิดถึงต้นฉบับจริง อ้างอิงที่หาต้นฉบับไม่ได้ให้ทำเครื่องหมายและรายงาน ห้ามเดา
   หรือสร้างรายการอ้างอิงขึ้นเอง
6. **ทุกการ cite ต้องมีเนื้อความจริงในต้นฉบับที่อ้าง** ข้อความที่ cite ต้องตรงกับสิ่งที่
   แหล่งนั้นกล่าวจริง ตรวจจาก PDF/ลิงก์ และบันทึกตำแหน่ง (หน้า/section) ที่รองรับ
   ถ้าแหล่งไม่ได้กล่าวเช่นนั้นหรือกล่าวอ่อนกว่า ให้รายงานว่า citation ไม่รองรับ claim
   บันทึกผลตรวจทุก key ลง `evidence/citation-audit-<date>.md` ตาม `templates/citation-audit.md`
   (verdict SUPPORTED/PARTLY/NOT/CANNOT CHECK พร้อม quote และหน้า) session ถัดไปอ่านไฟล์นี้ก่อน
   และตรวจซ้ำเฉพาะ key ที่ PDF hash หรือประโยคที่อ้างเปลี่ยน อ่านข้อความ PDF จาก cache
   ผ่าน `scripts/apk.py extract` และเมื่อแบ่งงานให้ subagent ให้แนบ
   `prompts/snippets/EXTRACT_FIRST_BRIEF.md` ใน brief
7. **ไม่สร้างตัวแปรลอยเพื่ออ้างอิงภายใน** ห้ามตั้งชื่อย่อ ตัวแปร หรือรหัสขึ้นมาเพียง
   เพื่ออ้างย้อนในบทความ เช่น “เรียกค่านี้ว่า α” แล้วใช้ α ต่อโดยไม่จำเป็นทางคณิตศาสตร์
   เพราะเพิ่มภาระความจำของผู้อ่าน ให้เรียกสิ่งนั้นด้วยชื่อที่มีความหมาย (ดูหัวข้อชื่อที่สื่อความหมาย)
8. **ทุกรูปต้องบอกชัดว่าให้ดูอะไร ตรงไหน** ข้อความและ caption ชี้ส่วนของรูปที่เป็นหลักฐาน
   ของประเด็น เช่น แผง ช่วงเวลา บริเวณ หรือเส้น และอาจใช้ callout (ลูกศร กรอบ ป้ายกำกับ)
   ในรูปเพื่อชี้จุดนั้น รูปที่ไม่มีจุดให้ดูชัดเจนให้รายงานเป็นจุดต้องแก้
9. **ศัพท์เทคนิควงเล็บภาษาอังกฤษที่ตำแหน่งแรก** เช่น “การไหลเชิงแสง (optical flow)”
   หลังจากนั้นใช้คำไทยเดิมตลอด ถ้าไม่มีคำไทยที่แพร่หลาย ใช้ทับศัพท์แล้ววงเล็บภาษาอังกฤษครั้งแรก

**การแปลกลับเป็นภาษาอังกฤษ** เมื่อร่างไทยผ่าน review แล้วต้องแปลกลับเป็นต้นฉบับอังกฤษ
ให้คงรูปประโยค การเลือกใช้คำ และลำดับลอจิกที่ใช้อธิบายของร่างไทยไว้ ประโยคเปิดที่เป็น
punch line ต้องยังเป็นประโยคเปิดของย่อหน้าเดิม ลำดับย่อหน้าและลำดับเหตุผลภายในย่อหน้า
ต้องตรงกับร่างไทย ศัพท์ที่วงเล็บไว้ใช้คำอังกฤษนั้นตรง ๆ และคงที่ตลอด ห้ามเรียบเรียงใหม่
รวมหรือแยกประโยค สลับลำดับ หรือเปลี่ยนคำให้ฟังสละสลวยขึ้นจนน้ำหนักหรือความหมายต่างจาก
ร่างไทยที่ review แล้ว ถ้าโครงประโยคไทยใช้ในภาษาอังกฤษไม่ได้ ให้ปรับเท่าที่ไวยากรณ์บังคับ
และรายงานจุดที่ปรับแยกไว้

ตัวตรวจ `--profile academic` รายงานคำลดคุณค่างาน (เพียง/แค่/ยังไม่ได้, merely, only a few)
และป้ายรหัสลอย (RQ1, R1, T1, C2) เป็น `review` candidates ให้อ่านทุกจุดในบริบท

ส่งร่างไทยพร้อมบันทึก review แยกต่างหาก ที่สรุปจุดเด่น จุดด้อย ย่อหน้าที่หลุดประเด็น
คำที่ยังไม่นิยาม อ้างอิงที่เข้าถึงไม่ได้หรือไม่รองรับ claim รูปที่ไม่มีจุดให้ดู และความเห็น
เรื่องขอบเขตงานตามข้อ 3

## B. Scientific pre-pass สำหรับงานวิชาการ

1. **ตรึง evidence boundary** แยกสิ่งที่ source กล่าวโดยตรง ข้ออนุมาน และสิ่งที่ยังไม่ทราบ
2. **ทำ method/lineage pass ก่อน style pass** ตรวจ input → processing → parameter → output → claim;
   ถ้ามีวิธีเปลี่ยน ให้ตรวจผลปลายน้ำก่อนล็อกเนื้อหา
3. **ทำ artifact/provenance pass** แทนคำภายในด้วยวัตถุจริง และเติม scientific justification
   หรือระบุสถานะ operational/uncalibrated อย่างตรงไปตรงมา
4. เมื่อ pre-pass พบปัญหา ให้แก้หรือรายงานแยกก่อนล็อกเนื้อหา ห้ามกลบปัญหาด้วย style edit
5. **ทำ semantic naming pass** ตรวจทั้งต้นฉบับ รูป ตาราง และเอกสารเสริมว่าไม่มี
   การอ้างรหัส config หรือรหัสคำถามวิจัย และชื่อทุกชื่อสื่อสาระได้โดยไม่ต้องจำรหัส
6. **ตรวจน้ำเสียงและความเป็นธรรมของคู่เทียบ** แทนคำลดคุณค่างานตัวเองด้วยข้อเท็จจริง
   และตรวจว่าทุกวิธีได้รับการรายงานด้วยเกณฑ์เดียวกัน ไม่มีการเน้นหรือเลือกเล่าที่ชี้นำ
   ให้คู่เทียบใดโดดเด่นเป็นพิเศษ ความแตกต่างที่สรุปต้องสืบกลับถึงผลและเงื่อนไขได้
7. **ตรวจโครงสร้างหลังการแก้หลายรอบ** ไม่มีคู่เทียบได้รับ section เฉพาะหรือน้ำหนัก
   เพิ่มเพียงเพราะถูกกล่าวถึงทีหลังหรือบ่อยกว่าในแชต การแยกหัวข้อต้องมีเหตุผลด้าน
   เนื้อหาหรือคำสั่งชัดเจน และยังต้องผ่านเกณฑ์รายงานคู่เทียบอย่างเป็นธรรม
8. **ตรวจสัดส่วนความสำคัญทั้งฉบับ** ทุกประเด็นได้รับน้ำหนักตามคำถามวิจัย ผลกระทบ
   ต่อข้อสรุป และหลักฐาน ไม่มีรายละเอียดรองกลายเป็นประเด็นหลักจากความยาวหรือ
   ความถี่ของการคุย รวมถึงในชื่อเรื่อง บทคัดย่อ และบทสรุป
9. **ตรวจอ้างอิงและรูป** ทุกอ้างอิงมี PDF หรือลิงก์ถึงต้นฉบับ ทุก claim ที่ cite มีเนื้อความ
   รองรับจริงในแหล่งนั้น และทุกรูปบอกชัดว่าให้ผู้อ่านดูอะไร ตรงไหน

## C. รายงานผล

สำหรับงานวิชาการ ให้รายงานผล scientific pre-pass แยกจาก pattern counts และอ่าน `review`
candidates ทุกจุด ถ้า style pass พบปัญหาเนื้อหา ให้ย้อนกลับไป method/lineage pass
